# Mochi 用户体验设计说明

版本：v0.1 · 日期：2026-11-11 · 状态：目标体验草案

飞书版本：[Mochi 用户体验设计说明](https://d5abb0zl2u.feishu.cn/docx/FcRmdTAJqo8iyqxS2u2cN45enRf)，位于「我的文档库」。

本文从用户视角描述 Mochi 最终提供什么、如何交互，以及怎样判断体验是否成立，供产品讨论、C 的界面实现和演示验收使用。文中的“目标核心”来自现行产品方案；“交互建议”是尚未冻结的界面安排；“可选扩展”不计入基本产品承诺。当前 M0 的实际边界见第 7 节。

## 1 产品定位与体验目标

Mochi 是面向学生和知识工作者的桌面工作伙伴：一只常驻桌面的像素小猫，帮助用户登记事项、选择提醒时机、管理专注节奏，并在工作结束后回顾进展。用户说明要做什么、时间边界和允许的打扰程度，产品负责记住约定并保持用户可控。

用户需要得到三种明确感受：重要事项有确定的提醒时限；可以稍晚的事项尽量避开忙碌时刻；任何时候都能修改、延后、取消或纠正系统判断。Mochi 的人格体现在动画与措辞上，事项、时间、操作按钮和结果必须清楚准确。

日常使用不要求用户理解模型、工具调用或内部状态机。简单操作立即反馈，复杂事项在必要时询问，系统对用户状态的推测始终可以被用户纠正。

## 2 界面组成与入口

建议以“桌面小猫、交互卡片、工作面板”组织正式产品，保留像素风格。三者共享同一份任务和工作段状态；用户在任何入口做出的修改，应同步到其他入口。入口手势尚未冻结，需与现有的抚摸、点击和拖拽行为一起验证。

| 界面 | 用户看到什么 | 何时出现、如何操作 |
| --- | --- | --- |
| 桌面小猫 | 陪伴动画、简短提示、打开助手的入口 | 平时保持轻量存在；保留抚摸和拖拽。建议通过明确的菜单或入口打开输入区，具体手势待定 |
| 小猫旁的交互卡片 | 事项确认、歧义选项、提醒内容、工作段结束提示 | 需要确认或发生提醒时出现；提供明确按钮，后台刷新不抢用户正在输入的焦点 |
| 工作面板 | 事项输入、待办列表、工作段计时、回顾、状态和设置 | 用户主动打开后编辑；支持从提醒卡返回对应事项 |

工作面板中的常用信息应直接可读，例如“今天 17:00”“最晚 17:20 提醒”“已延后至 17:30”。原始信号、证据 JSON、事件编号和版本等信息留在联调台或诊断入口，普通用户通过“判断依据”查看简明解释。

## 3 用户可见的核心功能

| 功能 | 用户如何表达或操作 | 产品反馈 |
| --- | --- | --- |
| 自然语言登记事项 | 输入“今天五点提醒我交报告” | 生成可编辑确认卡，列明事项、完整日期、时间、时区和提醒方式；有歧义时先询问 |
| 强提醒 | 选择“到点提醒”，确认确切时间 | 到点展示事项和操作按钮，不因系统估计用户忙碌而自行推迟 |
| 柔性提醒 | 输入“五点左右提醒我买牛奶”，确认允许窗口 | 在批准的时间窗内寻找适合提示的机会；到最迟时间仍展示提示 |
| 待办管理 | 查看、修改、延后、取消、标记完成 | 显示最新安排与状态，立即反馈操作结果，取消或修改后的旧结果不能恢复旧事项 |
| 状态查看与纠正 | 查看“估计正在专注”等状态，改为“我在开会”或“现在可以打扰”并设置持续时间 | 展示用户纠正及其截止时间；纠正有效时优先采用，到期后重新使用当时可用的估计 |
| 工作段与番茄钟 | 设定目标和时长，开始、暂停、继续、结束 | 显示阶段和剩余时间；暂停不消耗时长，短暂切换应用不重置工作段 |
| 工作回顾 | 结束工作段，确认已完成项并补充结果、未完成项和下一步 | 展示可修改的回顾，保存用户确认的内容；结束工作段不自动完成关联事项 |
| 任务保留与恢复 | 重新打开应用，查看此前安排 | 恢复已保存的事项与工作段状态；错过提醒需说明实际情况并按约定处理 |

“完成”“延后”和“取消”具有不同含义：完成表示用户确认事项已经做完；延后表示继续保留事项并改变下一次提醒时间；取消表示停止后续提醒。卡片出现、消失或被关闭，都不能替代用户的完成确认。

## 4 典型用户旅程

### 4.1 登记并处理一条柔性提醒

场景：用户正在写论文，希望下班前买牛奶，又不想在写作中途频繁被打断。下表中的 17:00–17:20 是用户确认的示例窗口，不是系统默认替所有用户决定的宽限时间。

| 阶段 | 用户动作或状态 | Mochi 的可见回应 |
| --- | --- | --- |
| 输入 | 输入“今天五点左右提醒我买牛奶” | 立即显示输入已接收，进入事项理解；已有任务和其他按钮仍可操作 |
| 确认 | 查看并确认“今天 17:00–17:20，尽量在不忙时提醒” | 显示可编辑的事项、日期、窗口和提醒方式；确认后加入待办 |
| 等待 | 17:00 仍在写作 | 保留提醒，暂不主动打断；用户打开面板时能看到最迟提醒时间 |
| 提醒 | 在窗口内出现适合提示的机会 | 小猫旁展示“买牛奶”，提供“已完成／稍后提醒／修改／取消” |
| 兜底 | 到 17:20 仍未发现机会 | 按已确认约定展示低打扰提示，不继续无限等待 |
| 处理 | 点击“稍后提醒”，确认延后 10 分钟 | 显示新的提醒时间并更新待办；点击“已完成”则进入完成状态 |

如果用户输入的是“17:00 一定提醒我交报告”，确认卡应明确显示强提醒，到点直接展示。专注状态和用户的临时忙碌纠正不会自行改变这个时间承诺；用户可以主动修改事项的提醒安排。

### 4.2 开始并回顾一段专注工作

用户打开工作面板，输入“完成论文的方法部分”，选择时长并开始。面板显示目标、当前阶段和剩余时间，小猫可以用简短反馈表示开始，不要求用户保持面板一直打开。

中途有事时，用户暂停；继续时从剩余时长接着计时。切换应用本身不代表离开或结束。自动离开暂停等行为需有单独确认的规则，不能用没有键鼠输入来断言用户停止工作。

工作时间结束时，卡片提供“开始休息”“继续一会儿”“结束本轮”等选择，具体按钮与延长时长仍需在正式番茄钟流程中确定。用户提前结束也可以进入回顾，确认实际完成项、补充未完成内容并填写下一步。系统不会仅根据使用过某个应用就宣称用户完成了目标。

### 4.3 纠正一次错误的状态判断

用户正在阅读材料，系统却估计其可被打扰。用户打开状态入口，选择“我正在专注”，填写或选择原因，并设定持续时间。界面显示“按你的设置保持专注至……”，基础估计的依据仍可查看。

用户可以提前清除纠正。到期或清除后，产品根据当时仍有效的观察重新估计；缺少可靠依据时显示“暂时无法判断”。单次纠正改变的是当前策略输入，不自动证明模型已学会这一偏好。

## 5 交互与反馈规则

**关键承诺先确认。** 自然语言可以减少填写，但日期、时区、强弱模式或容忍窗口不明确时，必须用用户可理解的选项确认。“五点”不能悄悄变成某个日期，“左右”不能被默认为无限延后。

**操作立即反馈。** 输入先回显，按钮显示处理结果；理解事项所需的等待不应阻塞查看、编辑和取消。取消后显示已取消，旧卡片和迟到的模型结果不能重新改变该事项。

**状态需要表达不确定性。** 使用“估计正在专注”“估计可打扰”“离开”“暂时无法判断”等措辞，并提供简明依据和最近更新时间。用户明确设置、系统推测和无有效依据应有可辨别的呈现。

**展示和完成分开。** 提醒可显示为“已提醒，待处理”；只有用户明确完成才进入已完成。关闭卡片保留事项，具体后续催办节奏需另行确定；同一提醒重复投递时不应堆出多张相同卡片。

**后台刷新不抢焦点。** 用户主动打开输入区时获取输入焦点；状态更新和提醒到达时保持正在使用的其他应用可继续输入。多个提醒应各自保留事项和按钮，不互相覆盖；展示排序待进一步确定。

**人格表达不遮挡事实。** 可以说“该买牛奶啦”，但事项、时间和操作标签必须准确。按钮不使用让人猜测含义的角色台词，用户应能预判操作后果。

## 6 自动模式、权限与异常体验

建议默认采用手动开始工作段。自动番茄钟由用户主动开启，界面应解释观察什么、何时可能建议或开始一轮，并提供清晰的关闭入口。启用后是“先建议、再确认”还是“直接开始”，仍属于待确认的产品决策；关闭自动模式后不再残留自动启动行为。

感知设置需要说明采样范围、用途，以及哪些摘要可能交给云端模型。默认不记录按键原文或文件内容；若采用截图或其他更敏感输入，应提供明确的启用说明。缺权限时说明哪些判断不可用，同时保留手动状态、事项管理和工作段操作。不能把调用云端模型的方案描述成所有数据均不离开本机。

| 情况 | 用户应看到的反馈 | 仍然可做的操作 |
| --- | --- | --- |
| 日期或时间含糊 | 明确的日期、时间或窗口选择，不直接建立错误承诺 | 修改输入、选择选项或取消登记 |
| 感知缺失、过期或判断不确定 | “暂时无法判断”，可查看原因 | 手动纠正状态；强提醒仍按确认安排执行 |
| 模型超时或暂时不可用 | 说明理解尚未完成，提供结构化填写；已确认的强提醒继续走调度 | 查看、编辑、取消、延后、手动开始工作段 |
| 思考过程中用户已修改或取消 | 保留最新操作结果，旧结果不覆盖 | 继续操作当前事项 |
| 睡眠、退出或重启导致错过时机 | 说明哪些提醒未能按时展示，按已确认的恢复策略处理 | 查看事项、重新安排、完成或取消 |

本版时限承诺以应用运行、电脑唤醒且桌面可访问为前提。关闭客户端后的后台提醒或锁屏交付需要独立设计，不能在产品文案中承诺已经具备。自动恢复也不能把错过的提醒记成已按时完成。

## 7 当前 M0 与目标体验的关系

联调台是开发与验收工具。它保留任务、观察和事件诊断，C 的正式界面可以通过组件插槽接入同一后端，方便核对同一工作段和提醒在不同视图中的表现。正式用户界面不需要呈现这些工程信息。

| 体验能力 | 当前 M0 可验证的部分 | 目标产品仍需接入的部分 |
| --- | --- | --- |
| 事项与提醒 | 结构化输入、确认、到期展示、完成／延后／编辑／取消及旧结果拒绝 | 正式自然语言理解、SQLite 持久化、重启与睡眠恢复 |
| 状态判断与纠正 | 可替换采样和估计器、规则基线、证据与期限、人工纠正 | 真实 Jev／System 2、经标注验证的状态理解与打扰策略 |
| 工作段 | 手动开始／暂停／继续／结束、共享时钟、确认成果样例 | 完整工作／休息周期、自动模式、正式回顾与恢复 |
| 产品外观 | 固定 Qt 联调壳、可嵌入的 C 界面样例 | 正式动态组件渲染、像素风产品布局、旧桌宠与新后端的整合 |

## 8 可选扩展与待确认决策

可选的 SOP／skill 方向由用户主动选择记录步骤和材料，在确认的记录上生成总结、标准操作流程和 skill 草稿，经用户审阅、验证后再导出或启用。它不要求持续录制所有桌面活动，也不影响基本提醒与番茄钟是否可用。

| 待确认项 | 本文的交互建议或约束 |
| --- | --- |
| 如何打开助手 | 提供明确入口，与现有抚摸、点击和拖拽行为分开验证；具体手势待定 |
| 自动番茄钟如何启动 | 必须用户先开启；建议优先验证“建议开始”，是否提供直接开始模式再确定 |
| 关闭提醒卡后怎么办 | 关闭不等于完成；是否持续显示待处理、何时再次提示需要确定 |
| 延后与重复催办 | 用户明确看到新的提醒时间；延后上限、默认时长和催办次数待定 |
| 多个提醒同时到达 | 各自保留事项与动作，不覆盖；优先级、堆叠和排序待定 |
| 睡眠与重启后的恢复 | 说明实际错过情况；补发、合并与用户确认策略需要进一步确定 |

以上项目是产品决策清单，不表示已冻结或已实现。

## 9 用户体验验收场景

下表用于评审与演示目标体验，不能把联调台的模拟通过直接记为正式用户体验验收通过。

| 编号 | 演示情境 | 用户可观察的通过条件 |
| --- | --- | --- |
| UX-01 | 输入一条含糊的提醒 | 能在确认卡选择明确日期、时间和模式，确认前不作出未授权的时间承诺 |
| UX-02 | 用户忙碌时强提醒到期 | 在应用正常运行条件下按确认时间展示，用户仍能继续操作原应用 |
| UX-03 | 柔性提醒窗口内持续忙碌 | 允许窗口内择机提示，最迟时刻不再无限等待 |
| UX-04 | 模型思考期间修改或取消 | 最新选择立即可见，旧结果不恢复已取消任务、不改回旧时间 |
| UX-05 | 阅读时被误判为可打扰 | 能查看简明依据、纠正并设置期限；到期后不继续冒用旧依据 |
| UX-06 | 工作段暂停后再继续 | 暂停期间剩余时间不减少，继续后正确计时；切换应用不重置 |
| UX-07 | 结束工作段 | 用户确认成果与下一步，回顾反映这些内容，关联事项不被自动完成 |
| UX-08 | 同一提醒重复到达或旧卡片晚点 | 不出现多张相同提醒，旧操作不能改变新版事项 |
| UX-09 | 关闭自动模式或缺少感知权限 | 不再自动启动工作段，手动功能仍可使用，状态缺口可理解 |
| UX-10 | 在提醒卡、工作面板等入口之间切换 | 同一任务和工作段显示一致，提醒只有一个正式展示结果 |
